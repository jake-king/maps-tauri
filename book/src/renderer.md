# The native renderer

The pipeline: PMTiles archive → vector tile decode → meshes and labels (all Rust, in `crates/vtile`)
→ a binary response on `tiles://` → upload and draw (WebGL2, in `src/rust-renderer`).

## Reading and decoding

`pmtiles.rs` and `mvt.rs` are hand-rolled: each format is a few pages of spec, and owning the
decoder is what lets the renderer control allocation. `flate2` does the gzip. The spec's own examples
(tile ids, varints, the MVT geometry example) are unit tests and doctests.

The real check is a differential test, `tools/mvt_diff.mjs`. Every tile of an extract is read and
decoded by two independent pipelines, the Rust one and pmtiles.js with `@mapbox/vector-tile` (the
decoder MapLibre 6.7.0 itself uses), and compared layer by layer: features, geometry types, rings,
vertices, a coordinate checksum, extent and `kind` values. All 142 tiles and 926 layers are
identical. A planted bug (coordinate deltas read without their sign) turns 833 layers red. The diff
also corrected an assumption: `@mapbox/vector-tile` closes a polygon ring by repeating its first
point, and the Rust decoder now does the same.

## Meshing

`mesh.rs` turns a decoded tile into two GPU-ready meshes:

- **Fills.** Rings are grouped into polygons with holes by winding (as MapLibre's `classifyRings`
  does) and triangulated with `earcutr`, a port of the earcut MapLibre uses. Over a whole archive,
  25,300 of 25,302 polygon features triangulate to exactly their area; the other two, self-touching
  polygons, are within 0.5%.
- **Lines.** Two vertices per point, pushed apart along the miter (capped so sharp corners do not
  spike). The width is applied in the shader, so a mesh never needs rebuilding when the zoom changes.
  Road casings and dashed railways are built here too.
- **Colours.** Vertices carry palette indices, not colours, so a whole tile draws in two calls, one
  for fills and one for lines. The palette (`palette.rs`) is generated by `tools/gen_palette.mjs` from
  the same Protomaps style MapLibre draws, so the two renderers share colours, line widths by zoom,
  and draw order; the gate fails if the generated file and its generator disagree.
- **Labels.** Rust chooses label anchors while meshing: place names at their points, and for a street
  or stream name the longest piece of its line inside the tile, simplified (Douglas-Peucker, at most
  32 points) and oriented to read left to right. Only anchors inside the tile's own extent are sent,
  so neighbouring tiles do not repeat a label.

The result is serialised in a compact wire format (version 5, documented at the top of `mesh.rs`):
6-byte fill vertices and 8-byte line vertices with 16-bit tile coordinates, 16-bit indices unless a
tile passes 65,535 vertices, and a label block. The first version, with full colours and 32-bit
indices, was about 70% larger.

## Drawing

`renderer.js` fetches meshes, uploads them as they arrive (the only parsing in JavaScript is the
header) and draws two calls per tile. Each tile is clipped to its own square with the stencil
buffer (a scissor rectangle could not follow the map's rotation). A tile still loading is drawn by
its nearest loaded ancestor, clipped the same way, so the screen never shows unloaded background
while a coarser tile exists. A ring of tiles one beyond the view, and the tiles one zoom ahead while
zooming, are requested at low priority, so a tile is usually ready before it becomes visible.

Labels are placed in the frontend (`labels.js`): which labels show at a zoom, greedy collision in
priority order over a grid, and curved names laid out character by character along their path. They
are drawn on a 2D canvas over the map with the browser's text rendering, which gives full Unicode
shaping, Japanese included, without a glyph atlas.

Everything happens in one frame loop (`loop.js`): each display frame takes in what arrived (uploads
within a 4 ms budget, most urgent first), runs updaters such as animations, and redraws only when
something changed. Ticking every frame without drawing measured the same idle CPU as drawing on
demand (4.0% of a core), against 65.7% for drawing every frame.

## Measured against MapLibre

On the pan benchmark (a fixed route at the Santa Monica Pier), when the native renderer first drew
fills and lines:

| | MapLibre | native |
|---|---|---|
| memory at rest | ~500 MB | 296 MB |
| memory after the pan | ~700 MB | 340 MB |
| render CPU per frame, avg / p95 | 4.7 / 8 ms | 0.5 / 1 ms |
| tile request to drawable, avg / p95 | 37 / 60 ms | 14 / 24 ms |

Labels, icons, shields, casings and the search box came later and cost something: render time rose
to about 3 ms a frame and idle memory to 337 MB (with the dev overlay closed). The seeded stress
comparison in [Measuring](measuring.md) is the current head-to-head.

What it costs: the renderer, the mesher and the label placement are code to own, and MapLibre still
does some things better (it searches harder for room on a tight curve, and keeps kerning there).
